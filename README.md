# 2026-10-9-Yi · 变易

一个以《易经》六十四卦为主题的互动网页项目。从太极一下一下点出生两仪、四象、八卦，
重卦成六十四卦，再逐爻抽出一卦，最后展开这一卦的「错综」关系网——每种变法都在一个
**展示位**上当场演算给你看。

视觉约束：**仅黑白灰，靠明度多层次区分（tone ramp）**；交互形式：单文件 HTML，零依赖。

https://taiji009.github.io/2026-10-9-Yi/

## 六屏流程

| 屏 | `data-screen` | 内容 | 交互 |
|---|---|---|---|
| 0 | `rest` | 太极呼吸 | **单击一下**太极即起卦 |
| 1 | `generate` | 生演：太极 → 两仪 → 四象 → 八卦 | **点击驱动**：点一下长出一个新卦，共 14 次；可随时**跳过** |
| 2 | `matrix` | 重卦：六十四卦方阵 | 静态展示；点「继续 · 起卦」进入下一屏 |
| 3 | `cast` | 起卦：六爻自下而上逐爻抽取（大衍筮法） | 每爻「蓄—落—显」三段节奏；可**跳过**直接落定 |
| 4 | `settle` | 成卦：本卦 + 之卦，**各带卦名** | 点「展开错综 · 十五卦」进入下一屏 |
| 5 | `network` | 错综演算：三栏对照 + 展示位 | **点击**任一卦卡，展示位当场演算那种变法；可「重新起卦」 |

键盘：屏 0 `Enter`/`Space` 等效于单击；屏 1 可点节点都能 `Tab` 聚焦、`Enter`/`Space` 触发；
任意屏 `Esc` 跳过。

## 屏 1：点击驱动的抽卡生长

金字塔**倒置**——太极在最下、八卦在最上，一层层往上长。

- 点太极 → 抽出一爻，得到第 1 个「仪」；再点一次 → 必出另一个（因为只有两种）。
  **先抽出的那个在左边**，所以左右顺序由第一抽决定，不是固定的「阳左阴右」。
- 点某个「仪」→ 其上叠加抽一爻，裂变出一个「四象」；再点同一个 → 出另一个。四个四象抽完进下一层。
- 点某个「四象」→ 同理裂变出八卦。8 次点完，共 8 个八卦。

**第 2 个子节点的新爻 = 第 1 个的反**（不是再次随机）。这保证了一个不变量：
**第 d 层恰好 `2^d` 个互不相同的节点**——子节点继承父的下方若干爻，所以父不同则子不同；
同一父的两个子在新爻处一阴一阳，也不同。于是两仪恒 2、四象恒 4、八卦恒 8，正是「加一倍」。
`?debug` 里有一条断言专门验证这个不变量。

每次抽爻是「**蓄 → 抽/裂变 → 落/显**」三段（720/560/520ms）。抽完即解锁，第 3 段作为尾巴
与下一次点击并行——所以感知间隔约 1.1 秒，不是 1.8 秒。嫌慢/嫌快只改 `DATA.DUR` 的三个常量。

尺寸按 `DATA.GROW` 公式预算，不测量：`x(col,d) = (col+.5)/2^d * W`、`y(d) = Y0 - d*RH`。
宽度校验：`8×84 + 7×41 = 959 ≤ 1000`，留 20px 余量（**再加到 96 就会溢出**）。

## 屏 2：六十四卦方阵

- 8×8。**行列顺序都是先天生成序** `乾、兑、离、震、巽、坎、艮、坤`（即 `RULES.generationOrder()`）。
- 行 = 上卦、列 = 下卦。第 `row` 行第 `col` 列 = `[...列首的bits, ...行首的bits]`（下卦在前）。
- 卦象与屏 1 **同尺寸**（宽 84 / 线厚 6 / 间距 11），两屏视觉连续。
- 与屏 1 相互独立：屏 1 顶端 8 个八卦的顺序是**随机**的，本屏是**固定**先天序，两页不一致是有意为之。

## 屏 5：错综演算

```
                 综卦  错卦  交卦          ← 顶排
 变·上爻
 变·五爻                                   互·去初
 变·四爻     ┌────────┐  ┌──────────┐      互·去上
 变·三爻     │  本卦  │  │ 展示对比卦 │      互·去初上
 变·二爻     └────────┘  └──────────┘      互·去初二
 变·初爻                                   互·去五上
```

- **左列 6 张变卦**，上→下 = 上爻→初爻（垂直位置 = 变哪一爻）。
- **默认态**：展示位是**之卦**（所有动爻一起变）。六爻皆静时之卦 === 本卦，语义坍塌，
  所以此时展示位留空并标注「无动爻」。
- **每张卡下方都有卦名**；本卦与之卦下方也各有卦名。
- 动爻在爻的**左侧**标一个「动」字（不再用 `○`/`×` 区分阴阳）。

### 五种变法的演算

| 点击 | 展示位上发生什么 |
|---|---|
| **变卦** | 本卦**平移到**展示位 → 对应那一爻翻转 |
| **错卦** | 本卦平移到展示位 → 六爻**同时**阴阳翻转，逐爻错峰 |
| **综卦** | 本卦平移到展示位 → **整卦旋转 180°** |
| **交卦** | 本卦的下卦移到展示位的**上**位、上卦移到**下**位，两条反向弧错身 |
| **互卦** | 先在**本卦上框选**被保留的爻区间 → 展示位从无到有淡显这些爻 → **裂变**成上下两个三爻卦叠加 |

点击任何新卦时，展示位原有的卦**先淡化消失**，新卦再按上表出现。

**互卦的裂变是参数化的**：目标第 `j` 爻的源下标 `src = (j<3 ? hu.lower[j] : hu.upper[j])`。
`lower`/`upper` 各 3 项 ⇒ 目标恒 6 个槽；但源只有 **4 或 5 个不同下标**（两者会重叠，
如「去初上」`lower=[1,2,3]`、`upper=[2,3,4]` → 源只有 {1,2,3,4}）。
一个源供两个目标时，那条爻必须**裂成两条**——正是「裂变」的视觉来源。
这套写法对 5 种模式**统一生效**，不需要为每种写死。

## 两个必须知道的架构决定

**① 展示位是「复制」，不是「移动」本卦。**
本卦必须原地可见且不变——用户还要继续点别的卡，移动会留空框、也没法连点。
复制体是绝对定位的一个独立爻栈，覆盖在本卦框上。

**② 错综页连点绝不能用 `ANIM.cancelAll()`。**
它是「切屏解药」，在这里调用会连带杀掉卡片入场尾帧，视觉上是「整屏一抖、尾巴消失」。
本屏改用局部 `SHOW.seq` + `cancelGuest()`，只取消在飞的复制体。
**这条与切屏的哲学相反，是最容易顺手写错的地方。**

**硬约束**：本卦框与展示位框必须**同行、等几何、固定 gap**。
由此三个量是常数、无需逐帧测量——平移量 `dx/dy`（初始化与 resize 各测一次）、
交卦错身量 `±3×(爻高+间距)`、互卦的「源爻 y ↔ 目标爻 y」可直接互换。
**一旦让两框几何不同，这三个公式全废。**

## 规则实现

**数据模型**：爻 = 1 bit，六爻自下而上 `[初,二,三,四,五,上]`，阳=1。

```
三爻值(0..7)  = b0 + b1*2 + b2*4     坤0 震1 坎2 兑3 艮4 离5 巽6 乾7
重卦值(0..63) = 下卦(内) + 上卦(外)*8   乾为天=63  坤为地=0
```

14 个变体全部由纯函数算出（见 `RULES`）：

| 变体 | 实现 |
|---|---|
| 变卦 | 翻转第 i 位 |
| 综卦 | 数组倒序 |
| 错卦 | 逐位取反 |
| 交卦 | 交换低 3 位与高 3 位 |
| 互卦 ×5 | 按 `HU_MODES` 参数化下标抽取两个三爻子数组 |

**卦名由 bits 反查，不由位置决定**（`RULES.bitsToTrigram` / `bitsToSixiang`）。
生演树是随机生长的，位置与卦不再对应，按位置贴名必错——这是 1.0 的一个隐性错误，2.0 已修。

**两套独立的随机**：

| 用途 | 规则 |
|---|---|
| 屏 1 生演抽爻 | **1/2 均匀**（阳或阴各半）；第 2 个子节点取第 1 个之反 |
| 屏 3 六爻起卦 | **大衍筮法**，非均匀（见下表） |

| 爻 | 数 | 概率 |
|---|---|---|
| 老阴 | 6 | 1/16 = 6.25% |
| 少阳 | 7 | 5/16 = 31.25% |
| 少阴 | 8 | 7/16 = 43.75% |
| 老阳 | 9 | 3/16 = 18.75% |

老阴、老阳为**动爻**：视觉上取全程最亮的纯白 + 光晕 + 呼吸，并在爻左侧标「动」字。
有动爻时，屏 4 会并列显示**之卦**（动爻全变之后得到的卦）。

## 自检

打开 `index.html?debug`，控制台会跑 24 条断言：卦名表、先天生成序、`bitsToTrigram`/`bitsToSixiang`、
15 格系统、综/错/互抽查、**生演不变量**（每层恰好 2^d 个互不相同的节点）、
16 万次采样验证大衍概率。

同一条命令也能在命令行跑，CI 用的就是它：

```bash
node scripts/check-rules.mjs
```

它不另抄一份断言，而是**从 `index.html` 里把 `?debug` 那段源码抽出来直接执行**，
外加结构冒烟（doctype / 标签配对 / 零外部依赖 / 无绝对路径资源）。
所以页面里跑什么，CI 就跑什么——改了一边另一边不可能漏。

也可以在控制台直接用 `window.YI` 里的
`DATA / RULES / STORE / RENDER / ANIM / GROW / STAGE / FSM / PLAYS` 调试：

```js
YI.RULES.bitsToName([1,1,1,1,1,1])             // "乾为天"
YI.RULES.buildVariants([1,0,1,0,1,0]).length   // 15
YI.RULES.generationOrder().map(t=>t.name).join('')  // "乾兑离震巽坎艮坤"
YI.GROW.counts                                  // 生演各层已生成数
YI.STAGE.SHOW.bits                              // 展示位当前显示哪一卦
```

## 代码结构

`index.html` 内部按命名空间分区，依赖严格单向：

```
DATA → RULES → STORE → RENDER → ANIM → GROW / STAGE → FSM → EVENTS → BOOT
```

- `RULES` 绝不碰 DOM；`RENDER` 绝不写 state；`ANIM` 不认识业务语义，只认 `el` + keyframes。
- `GROW`（屏 1 生演）与 `STAGE`（屏 5 错综）是两个状态控制器，只依赖 `RULES/RENDER/ANIM`，不碰 `STORE`。
- 动画主干用 WAAPI（`element.animate`）；`ANIM` 里有一个全局注册表 + `epoch` token——
  **切屏**时 `cancelAll()` 让所有在飞的 `await` 自动失效，这是跨屏串扰的解药
  （但屏 5 内部连点走的是另一套，见上）。

## 视觉约定

全站仅黑白灰，靠明度阶梯承载语义：

| 层级 | 语义 |
|---|---|
| L0 近黑 | 虚空 / 太极未分 |
| L1 极暗 | 卦位槽、网格、未占用的爻位 |
| L2 暗 | 静爻（少阳 7 / 少阴 8） |
| L3 中 | 次要文字、标签、卦名 |
| L4 亮 | 落定的爻、正文 |
| **L5 近白** | **动爻**、焦点、高光 |

阳爻 = 两段各占 50% 的线 `scaleX(1)` 拼成实线；阴爻 = 两段 `scaleX(.88)`，中缝裂开。
翻爻只 morph `scaleX`，不换 DOM、不产生 reflow。

生演的 SVG 爻线每爻包一层 `<g class="gen-line">`，配 `transform-box: fill-box`——
否则 SVG 的 `transform-origin` 默认在画布原点，`scaleX()` 会跑偏。

系统开启「减弱动态效果」时，所有时长乘以 0.15 并关掉抖动层——保留叙事，但不刺激。

## 部署

推送到 `main` 分支时，GitHub Actions 自动把 `index.html` 发布到 GitHub Pages
（工作流：`.github/workflows/deploy.yml`）。该工作流**只发布 `index.html`**，
`docs/`、`README.md`、`.claude/` 都不会进入站点。

首次启用需一次性配置：仓库 **Settings → Pages → Source** 选 **GitHub Actions**
（不要选 "Deploy from a branch"，否则部署会以 `Get Pages site failed` 失败）。
也可在 **Actions** 页选「部署到 GitHub Pages」→ **Run workflow** 手动触发一次。

## 协作流程

`main` 已设分支保护（ruleset `protect-main`）：**不能直接推送，改动必须走 PR**。
批准数设为 0，所以单人也能自己合并——GitHub 不允许批准自己的 PR。

1. 开分支：`git switch -c claude/<主题>`
2. 改完提交、推送：`git push -u origin claude/<主题>`
3. 开 PR：`gh pr create --base main`
4. 等「校验」工作流变绿（`.github/workflows/ci.yml`，跑 `scripts/check-rules.mjs`）
5. 合并（建议 **Squash and merge**，把分支上的多个提交压成一个进 `main`）

合并进 `main` 后，部署工作流才会触发，Pages 随之更新——PR 期间线上保持旧版。
